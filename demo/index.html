Your AI coding assistant, with rules it has to show.

UCA Kit is a folder of instructions and read-only scripts you install into a project. The assistant plans before it builds, checks its own work, and ends with a scorecard that says what it did not check.

01What changes when it is installed

The kit does not write code. It gives your assistant a short rulebook and a few tools, so the way it works becomes something you can see and check.

Plans first

A short plan before a new app: who it is for, the stack and why, the first small slice. At most three questions, each with a default.

Checks its work

It runs the project's tests and the kit's read-only checks, and says which ones it ran.

Owns up

It ends with a scorecard of Done, Left and Not checked, instead of "all done".

Hands off when stuck

A guard spots the same error twice or results getting worse, restores the last passing copy and writes a handoff for the next model.

03Install in three steps

You need Node.js 18 or newer. Run these in the root of your project.

  1. Preview. Lists every file it would write, and writes nothing.

    npx --yes github:crazy-creator0/uca-kit init . --platform generic --dry-run

  2. Install. Pick your tool with --platform, or leave it out to choose from a list.

    npx --yes github:crazy-creator0/uca-kit init . --platform generic

  3. Check it. Confirms every installed file is present, and lists any you have edited.

    npx --yes github:crazy-creator0/uca-kit doctor .

Set up for:

  • Claude Code
  • Cursor
  • GitHub Copilot
  • Gemini CLI
  • OpenAI Codex
  • OpenCode
  • Windsurf
  • Devin
  • JetBrains Junie
  • JetBrains AI Assistant
  • Any other tool (generic)

To remove it, run uninstall: it removes only the files it installed and keeps any you edited. Git is recommended but never required, and the kit asks before it runs git init.

05A task, step by step

For a new app, the assistant is told to follow the new-project workflow in .agents/workflows/new-project.md. This is the order it follows.

  1. Read. The request, attached files and the folder come first. Nothing already answered is asked again.
  2. Ask. At most three questions that change the build, each with a default so "go ahead" works.
  3. Plan. Who uses it, the main objects, the stack and why, the files, the first slice, and how it will be checked.
  4. Build one slice. One small working piece, not the whole app in one go.
  5. Check. Run the project's tests, then the Senior Bar check when installed.
  6. Scorecard. At most 12 lines: what is Done, what is Left, what was not checked.

The highlight only shows the order. It is not a progress bar.

06What gets installed

Rulebook

AGENTS.md and a short core in .agents/. Your tool's own file (for example CLAUDE.md or a Cursor rule) points to it.

Skills and workflows

Debugging, security review, design taste, databases, APIs and more, in .agents/skills/. Workflows for a new project, a feature, a bug, a deployment and a stack change.

Read-only scripts

The Senior Bar check, a design check, a project scanner and the handoff guard, in scripts/. They read files; the guard runs only the check you give it.

07Handoff guard

When you list several models in .uca/config.json, the assistant runs its checks through scripts/uca-guard.cjs. If it fails the same way twice, gets worse, or changes too much at once, the script prepares a handoff instead of letting the assistant keep guessing.

  1. Run the check through the guard, for example your test command.
  2. A trigger fires: the same error twice, results worse than before, three or more files changed, empty or garbled output, or a timeout.
  3. Snapshot of the current state goes to .uca/backup/ first.
  4. Restore the last passing copy, which the guard keeps itself. It never runs Git.
  5. HANDOFF.md is written from tool output only, with common secrets masked. No model writes conclusions in it.
  6. Switch message names the next model. After the last model it prints STOP and exits with code 4.

Exit codes: 0 passed, 1 failed with no trigger yet, 2 usage or config error, 3 handoff written, 4 stop.

The guard guards against honest mistakes. It is not a security boundary, and the redaction of secrets is best effort. A failure right after a pass counts as "worse", so it is strict.

08Senior Bar check

node scripts/uca-senior-check.cjs . looks at a project and reports the basics that are present or missing. It reads files only. It never runs your code, never writes, never opens .env or key files, and never prints a secret.

Each check is a plain yes or no. Hints, such as risky patterns like eval or innerHTML, are listed with file and line but not scored.

A high score does not prove a project is well built. A low one is a to-do list, not a verdict.

The 16 scored checks
  • Code is not piled into one big file
  • Dependencies are declared in a manifest
  • A README exists, and says how to run the project
  • .env files are kept out of Git, and an .env.example documents the settings
  • No secret is written into the source
  • Test files exist, and a test command is declared
  • Dependency versions are locked
  • A start or build command is declared, and the runtime version is declared
  • .gitignore keeps dependency and build folders out of Git
  • Images have alt, pages declare a language, and pages set a viewport

09What it does not do

No network

The installer and scripts send nothing anywhere. A test runs them with network calls blocked and fails if one is tried.

No hidden programs

No install-time scripts and no dependencies. The scripts call only read-only git; the guard and the scanner's --verify run only the command you name.

No surprise deletes

uninstall removes only files the kit installed, and never one you edited. An edited manifest cannot make it delete files outside the kit's own paths.

Details and how to report a problem: SECURITY.md.

10Limits

  • Not benchmarked. No scored runs against real models have been published yet. The benchmark kit is in the repository for anyone to run.
  • Host support is untested. The compatibility table in docs/TOOL-COMPATIBILITY.md marks every tool as untested until someone records a versioned test.
  • Instructions are not enforcement. A model can ignore them. The scripts are checks you can run yourself.
  • The static checks are shallow. They read text. They cannot tell whether code is correct or secure.
  • Mostly tested on Linux. Windows is covered lightly in CI.

11Questions

Does it work with my tool?

The installer writes the files each of the 11 listed tools reads, and a generic setup for any other tool. Whether a tool follows them has not been tested end to end yet, so treat support as untested.

Will it make my results better?

Unknown until real runs are published. In the samples, the with-kit runs left more of the basics, such as READMEs and design notes, and in one sample tests. Both sides were honest about what they had not checked. That is a few runs, not a measurement.

Does it send my code anywhere?

No. Everything is local files. The optional usage meter only stores counts that you, or a supported tool such as OpenCode, give it, on your own computer.

Which tier should I pick?

lite for small local models with about 8k tokens of context, standard for most models, full for large-context models. You choose it; the assistant never changes it. --context <tokens> prints a suggestion.

How do I remove it?

Run npx --yes github:crazy-creator0/uca-kit uninstall . --yes. Files you edited are kept.
