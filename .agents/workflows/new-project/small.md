## Small build
For a small request only: one file or one screen, one person using it, nothing shared with other users. Anything larger, or any doubt about the size, follows "Size the plan first" and the full Steps.

1. **Plan block, about six lines, before any code:** who uses it; their main task in 3 to 6 steps in their words, each with a concrete input and the result they expect (one input hard: long, a file from the tool they use, another language or the largest size), marked assumed unless the user said it; 3 to 5 extras a user of this kind of product would expect (for a game: best score, sound on/off, a pause key), each in or out; the stack; how you will check it. State your assumptions, ask at most one question and only if a wrong guess would be costly, then build. If the request names a product to match ("like X"), list the core features you know X has, each in or out.
2. **Stack:** one HTML file, plain CSS with variables, vanilla JS, data in `localStorage`; no build step and nothing loaded from the network. If the request needs more, use "Stack decision" in `frontend-engineering`.
3. **Look:** follow "Small build" in `design-taste-discovery` before writing the screen (`node scripts/uca-read.cjs design-taste-discovery --section "Small build"`; that skill's Read first is not needed).
4. **Build** the main task first, with believable data from the domain. Never drop a feature the user named.
5. **Check** each main-task step with "Check it like the user" in `testing-and-code-review` (`node scripts/uca-read.cjs testing-and-code-review --section "Check it like the user"`), at the highest level available, one Checks line per step, the hard input included.
6. **Finish, one pass, fixing what you find:** loading, empty and error states in plain words; input checked, with a message that says what to fix; usable at phone width, images with alt text, every control reachable by keyboard, and focus does not stay on a button that a key would press again; no eval or raw HTML from input; at least one check of a failure; every item the user asked for marked Done or Left with a reason. Mark nothing Done without opening the file or running it.
7. **Closing message, 300 words or less:** the R-FINISH lines first (Changed, Checks, Still unknown); no recap of the code, the plan or each step; never shorten Still unknown to fit. No README, readiness run or scorecard unless the user asked.
