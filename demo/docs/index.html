UCA Kit · field manual

Rules, checks and a paper trail for an AI coding assistant.

The kit is a set of instructions and small read-only scripts you install into a project. It makes the assistant plan first, check its work, and say what it did not check. It does not write code itself and it does not guarantee results.

01What it is

You install it once per project. Your coding assistant reads the instructions in that folder and follows them. The kit is plain files: a short core rulebook, optional skills for jobs such as debugging or design, workflows, and a few scripts that only read your project.

What you get, in practice:

  • A short plan before a new app is built, with at most three questions, each with a default.
  • A finishing scorecard that has to say Done, Left, or Not checked for each line.
  • A guard that notices when the assistant is stuck and prepares a handoff to another model.
  • A read-only checklist, the Senior Bar check, for the basics every project should have.

It is a set of instructions, so it is only as reliable as the model following them. Scripts check things in code. Instructions ask.

02Install

You need Node.js 18 or newer. Run this in the root of your project:

npx --yes github:crazy-creator0/uca-kit init . --platform generic

Omit --platform to choose from a list, or add --dry-run to preview the files without writing anything. Git is recommended but never required, and the kit asks before it runs git init.

To remove it later, use the installer's uninstall command. Files you edited are kept.

03A task, step by step

For a new app, the assistant is told to follow the new-project workflow in .agents/workflows/new-project.md. This is the order it follows.

  1. Read. The request, attached files and the folder come first. Nothing already answered is asked again.
  2. Ask. At most three questions that change the build, each with a default so "go ahead" works.
  3. Plan. Who uses it, the main objects, the stack and why, the files, the first slice, and how it will be checked.
  4. Build one slice. One small working piece, not the whole app in one go.
  5. Check. Run the project's tests, then the Senior Bar check when installed.
  6. Scorecard. At most 12 lines: what is Done, what is Left, what was not checked.

The highlight only shows the order. It is not a progress bar.

05Handoff guard

When you list several models in .uca/config.json, the assistant runs its checks through scripts/uca-guard.cjs. If it fails the same way twice, gets worse, or changes too much at once, the script prepares a handoff instead of letting the assistant keep guessing.

  1. Run the check through the guard, for example your test command.
  2. A trigger fires: the same error twice, results worse than before, three or more files changed, empty or garbled output, or a timeout.
  3. Snapshot of the current state goes to .uca/backup/ first.
  4. Restore the last passing copy, which the guard keeps itself. It never runs Git.
  5. HANDOFF.md is written from tool output only, with common secrets masked. No model writes conclusions in it.
  6. Switch message names the next model. After the last model it prints STOP and exits with code 4.

Exit codes: 0 passed, 1 failed with no trigger yet, 2 usage or config error, 3 handoff written, 4 stop.

The guard guards against honest mistakes. It is not a security boundary, and the redaction of secrets is best effort. A failure right after a pass counts as "worse", so it is strict.

06Senior Bar check

node scripts/uca-senior-check.cjs . looks at a project and reports the basics that are present or missing. It reads files only. It never runs your code, never writes, never opens .env or key files, and never prints a secret.

Each check is a plain yes or no. Hints, such as risky patterns like eval or innerHTML, are listed with file and line but not scored.

A high score does not prove a project is well built. A low one is a to-do list, not a verdict.

The 16 scored checks
  • Code is not piled into one big file
  • Dependencies are declared in a manifest
  • A README exists, and says how to run the project
  • .env files are kept out of Git, and an .env.example documents the settings
  • No secret is written into the source
  • Test files exist, and a test command is declared
  • Dependency versions are locked
  • A start or build command is declared, and the runtime version is declared
  • .gitignore keeps dependency and build folders out of Git
  • Images have alt, pages declare a language, and pages set a viewport

08Limits

  • Not benchmarked. No scored runs against real models have been published yet. The benchmark kit is in the repository for anyone to run.
  • Host support is untested. The compatibility table in docs/TOOL-COMPATIBILITY.md marks every tool as untested until someone records a versioned test.
  • Instructions are not enforcement. A model can ignore them. The scripts are checks you can run yourself.
  • The static checks are shallow. They read text. They cannot tell whether code is correct or secure.
  • Mostly tested on Linux. Windows is covered lightly in CI.
